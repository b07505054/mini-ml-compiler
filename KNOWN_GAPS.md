# Known Gaps

Last verified: 2026-07-15.

| Gap | Status | Publication wording |
|---|---|---|
| Universal policy engine | missing | P1D.1 and E3 are evidence-driven loops; many other decisions remain declared-profile, rule-based, shadow, or experimental. |
| Triton production integration | missing | Triton is shadow/provider-shaped with real artifacts, but not production Runtime dispatch. |
| Quantization scope | advanced partial | Static INT8 is materialized and executed for the validated fused Pi operator. Full-model accuracy, graph-wide mixed precision, INT4/AWQ/GPTQ, and NPU quantization remain absent. |
| AWQ plan consistency | known inconsistency | The positive AWQ plan has global AWQ/int4 intent while per-op entries contain fp16 fallback strategy text and int4 dtype fields. Do not claim complete INT4 support. |
| Capability DB canonicality | partial | Capability profiles are intended ownership, but compiler-local profiles remain richer and synchronization is incomplete. |
| Memory hierarchy / DMA / transfer model | missing | No mature memory-space/DMA/synchronization IR or bandwidth/transfer model. |
| NPU execution | missing | NPU profiles/plans are planning-only. |
| E2 correctness | invalid | Preserve invalid verdict. |
| E2.1 compiler-only interpretation | incorrect | Reclassify as implementation-stack comparison. |
| Fake `5.7 ms` ExecuTorch number | placeholder only | Must not appear as measured evidence. |
| General superiority claims | forbidden | No “beats ExecuTorch” or universal project/runtime superiority claim. |
| AArch64 native codegen: target-specific instruction selection (generic path) | missing | The AArch64 object generated by `--variant generic` for `hir.fused_matmul_bias_relu` (`artifacts/backend_codegen/aarch64_matmul_bias_relu_vectorized/generic/`) uses only generic LLVM lowering of unmodified Linalg-derived loops. No NEON, SDOT/UDOT, or FMLA intrinsic is emitted or selected for this variant. Do not describe the generic variant as vectorized or NEON-accelerated. The separate `--variant vectorized` path (see the two rows below) does produce real NEON `fmla`, but via LLVM's own instruction selector from stock MLIR vector-dialect lowering, not a project-owned instruction-selection pattern. |
| AArch64 native codegen: instruction scheduling / register allocation | missing | Scheduling and register allocation for both the generic and vectorized generated objects are entirely LLVM's stock `llc` behavior, unmeasured and uninspected by this project. No register-pressure, spill, or scheduling report exists for either variant. |
| AArch64 native codegen: runtime integration | missing | Neither the generic nor the vectorized generated AArch64 object is loaded by the C++ runtime's `OpRegistry`, and neither is a candidate in the compiler's cost model / plan selection. Both run only via standalone harnesses/test tools in `mlir_passes/tools/`, executed directly on the Raspberry Pi. |
| AArch64 native codegen: generic-path performance | measured, not competitive | On the real Raspberry Pi 5, the generic (unvectorized) generated kernel is slower (median latency) than an `-O2` scalar C++ reference across all three measured shapes (8x8x8, 16x16x16, 32x32x32) -- see `artifacts/backend_codegen/aarch64_matmul_bias_relu_vectorized/benchmark_<shape>.json`. This is expected given no unrolling/vectorization is applied in this variant; do not present the generic variant as a performance improvement over existing handwritten kernels. |
| AArch64 native codegen: vectorized-path scalability | known structural limit | `transform.structured.vectorize_children_and_apply_patterns` fully unrolls these fixed static shapes rather than emitting a strided loop over vector tiles, so vectorized object size and instruction count scale with M*N*K, not M*N*K/4 (32x32x32's vectorized object is ~64x the instruction count of 8x8x8's, ~113KB vs. ~2.2KB). This exact approach, unmodified, would not scale to large or dynamic shapes without adding explicit tiling before vectorization, which has not been implemented. See `artifacts/backend_codegen/aarch64_matmul_bias_relu_vectorized/README.md`. |
| AArch64 native codegen: multi-shape single-process benchmarking | resolved (previously known reliability limit) | Previously reported: running all three shapes' correctness+benchmark loops back-to-back in one process intermittently produced incorrect output on one shape. This has since been root-caused (an un-zero-initialized `linalg.matmul` accumulator in `mlir_passes/lib/MatMulBiasReluFusionPass.cpp`, triggered by heap-address reuse across repeated/mixed calls -- not an out-of-bounds write, not scheduler- or bufferization-specific) and fixed via explicit `linalg.fill` zero-init. Verified via 1000-call repeated-call tests and a 500-cycle (6000-call) mixed-shape/mixed-variant stress test with allocator noise, both variants, all shapes, zero failures. Cross-process isolation (`tools/run_backend_codegen_vectorized_pi_integration.sh`) is still used for benchmark timing methodology (avoiding cross-call timing interference), but is no longer required for correctness. See `artifacts/backend_codegen/aarch64_matmul_bias_relu_vectorized/README.md`. |
| Pre-existing, unrelated test failures | pre-existing, not introduced by the AArch64 codegen or vectorization slices | As of 2026-07-15, 20 `tools/run_mlir_pass_tests.sh` cases fail (88 total tests). The dominant cause (majority of cases) is a shared `linalg.map` operand/mapper-arity verifier rejection spanning canonicalization, fusion, and quantization test fixtures alike; a smaller cluster fails on `'hir.quantize' op requires integer attribute 'clamp_min'`; a few more are FileCheck attribute-string/output drift in serving and LLM-frontend-normalization fixtures. Verified identical failing-test names before and after the vectorization slice (zero new regressions). Out of scope for the AArch64 codegen/vectorization slices; needs its own fix. |
