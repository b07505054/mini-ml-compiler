# Known Gaps

Last verified: 2026-07-16.

| Gap | Status | Publication wording |
|---|---|---|
| Universal policy engine | missing | P1D.1 and E3 are evidence-driven loops; many other decisions remain declared-profile, rule-based, shadow, or experimental. |
| Triton production integration | missing | Triton is shadow/provider-shaped with real artifacts, but not production Runtime dispatch. |
| Quantization scope | advanced partial | Static INT8 is materialized and executed for the validated fused Pi operator. Full-model accuracy, graph-wide mixed precision, INT4/AWQ/GPTQ, and NPU quantization remain absent. |
| AWQ plan consistency | known inconsistency | The positive AWQ plan has global AWQ/int4 intent while per-op entries contain fp16 fallback strategy text and int4 dtype fields. Do not claim complete INT4 support. |
| Capability DB canonicality | partial | Capability profiles are intended ownership, but compiler-local profiles remain richer and synchronization is incomplete. |
| Memory hierarchy / DMA / transfer model | missing | No mature memory-space/DMA/synchronization IR or bandwidth/transfer model. |
| NPU execution | missing | NPU profiles/plans are planning-only. |
| E2 correctness | invalid | Preserve invalid verdict. |
| E2.1 compiler-only interpretation | incorrect | Reclassify as implementation-stack comparison. |
| Fake `5.7 ms` ExecuTorch number | placeholder only | Must not appear as measured evidence. |
| General superiority claims | forbidden | No “beats ExecuTorch” or universal project/runtime superiority claim. |
| AArch64 native codegen: target-specific instruction selection (generic path) | missing | The AArch64 object generated by `--variant generic` for `hir.fused_matmul_bias_relu` (`artifacts/backend_codegen/aarch64_matmul_bias_relu_vectorized/generic/`) uses only generic LLVM lowering of unmodified Linalg-derived loops. No NEON, SDOT/UDOT, or FMLA intrinsic is emitted or selected for this variant. Do not describe the generic variant as vectorized or NEON-accelerated. The separate `--variant vectorized` path (see the two rows below) does produce real NEON `fmla`, but via LLVM's own instruction selector from stock MLIR vector-dialect lowering, not a project-owned instruction-selection pattern. |
| AArch64 native codegen: instruction scheduling / register allocation | missing | Scheduling and register allocation for the generic, fully-unrolled vectorized, and tiled-vectorized generated objects are entirely LLVM's stock `llc` behavior. No project-owned scheduling or register-allocation pass exists for any variant. A design-time register-pressure PRECHECK exists for the tiled variant's 4x8x8 microkernel (`artifacts/backend_codegen/aarch64_matmul_bias_relu_tiled/register_pressure_32x32x32.txt`) -- it found zero spills but all 32 architectural vector registers in use in the hot loop (LLVM's own scheduler interleaves two K-sub-steps for ILP) -- but this is a one-shape sanity check, not a full register-pressure/spill-cost analysis. |
| AArch64 native codegen: runtime integration | missing | None of the generic, fully-unrolled vectorized, or tiled-vectorized generated AArch64 objects are loaded by the C++ runtime's `OpRegistry`, and none are a candidate in the compiler's cost model / plan selection. All run only via standalone harnesses/test tools in `mlir_passes/tools/`, executed directly on the Raspberry Pi. |
| AArch64 native codegen: generic-path performance | measured, not competitive | On the real Raspberry Pi 5, the generic (unvectorized) generated kernel is slower (median latency) than an `-O2` scalar C++ reference across all six measured shapes (8x8x8, 16x16x16, 32x32x32, 64x64x64, 32x64x32, 64x32x64) -- see `artifacts/backend_codegen/aarch64_matmul_bias_relu_tiled/benchmark_<shape>.json`. This is expected given no unrolling/vectorization is applied in this variant; do not present the generic variant as a performance improvement over existing handwritten kernels. |
| AArch64 native codegen: fully-unrolled vectorized-path scalability | resolved for practical shapes by the tiled slice | `transform.structured.vectorize_children_and_apply_patterns` with no tiling fully unrolls fixed static shapes, so object size and instruction count scale with M*N*K (32x32x32's fully-unrolled object is ~64x the instruction count of 8x8x8's, ~113KB vs. ~2.2KB; 64x64x64 was never built for this reason -- projected ~900KB). **Addressed** by `artifacts/backend_codegen/aarch64_matmul_bias_relu_tiled/` (tile+fuse+vectorize via stock Transform ops before LLVM lowering): 32x32x32 drops to 2,128 bytes (53.2x smaller) and 64x64x64 becomes practical (2,104 bytes), while measured Raspberry Pi latency is FASTER than the fully-unrolled kernel at every shape tested (median ratio 0.63-0.90x). The fully-unrolled variant is retained only as a historical/comparison baseline for the three original shapes, not as the recommended path. |
| AArch64 native codegen: tiled-path tail handling | missing (by explicit design, not oversight) | The tiled-vectorized variant's fixed 4(M)x8(N)x8(K) tile requires exact divisibility; shapes that do not divide evenly are REJECTED by `compile_hir_matmul_bias_relu_aarch64.sh --variant tiled-vectorized` with a nonzero exit and explicit error message (verified: M=N=K=10 rejected), never silently miscompiled. Use `--variant generic` or `--variant vectorized` for non-divisible shapes. General arbitrary-shape tail handling is not implemented. |
| AArch64 native codegen: tiled-path tile selection | missing | The 4x8x8 tile is fixed for all shapes, chosen once via a register-pressure estimate (see `artifacts/backend_codegen/aarch64_matmul_bias_relu_tiled/README.md`), not selected per-shape by any cost model. A different shape or target CPU could in principle prefer a different tile; this has not been explored. |
| AArch64 native codegen: multi-shape single-process benchmarking | resolved (previously known reliability limit) | Previously reported: running all three shapes' correctness+benchmark loops back-to-back in one process intermittently produced incorrect output on one shape. This has since been root-caused (an un-zero-initialized `linalg.matmul` accumulator in `mlir_passes/lib/MatMulBiasReluFusionPass.cpp`, triggered by heap-address reuse across repeated/mixed calls -- not an out-of-bounds write, not scheduler- or bufferization-specific) and fixed via explicit `linalg.fill` zero-init. Verified via 1000-call repeated-call tests and 500-cycle mixed-shape/mixed-variant stress tests with allocator noise, all variants, all shapes (including the tiled slice's 6-shape, 6000-call stress run), zero failures. Cross-process isolation is still used for benchmark timing methodology (avoiding cross-call timing interference), but is no longer required for correctness. See `artifacts/backend_codegen/aarch64_matmul_bias_relu_vectorized/README.md` and `artifacts/backend_codegen/aarch64_matmul_bias_relu_tiled/README.md`. |
| Pre-existing, unrelated test failures | pre-existing, not introduced by the AArch64 codegen, vectorization, or tiling slices | As of 2026-07-16, 20 `tools/run_mlir_pass_tests.sh` cases fail (94 total tests, up from 88 after this slice added 6 tiled-vectorized structural checks). The dominant cause (majority of cases) is a shared `linalg.map` operand/mapper-arity verifier rejection spanning canonicalization, fusion, and quantization test fixtures alike; a smaller cluster fails on `'hir.quantize' op requires integer attribute 'clamp_min'`; a few more are FileCheck attribute-string/output drift in serving and LLM-frontend-normalization fixtures. Verified identical failing-test names before and after this slice (zero new regressions). Out of scope for the AArch64 codegen/vectorization/tiling slices; needs its own fix. |
