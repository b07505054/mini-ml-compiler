# CPU Fused Schedule Candidate Discovery — Phase 1 Result

Roadmap phase: **Phase 1 — CPU Fused Schedule Candidate Discovery and Real Oracle**
(joint compiler roadmap across `ml-graph-compiler-runtime` and
`heterogeneous-inference-runtime`; this document covers `ml-graph-compiler-runtime` only).

Primary question: does the real CPU backend contain a meaningful, apples-to-apples
schedule-selection problem for one-pass fused MatMul+Bias+ReLU?

**Verdict: `FAILED_FOUNDATION`** — one candidate (`bm32_bn32_bk32`) dominates
26/30 raw rankings and is the only candidate to clear the noise floor
anywhere (1 stable win out of 30 workloads). This is reported as a valid
engineering result, not worked around.

All numbers below come from real measurements on this host, generated by
`apps/run_cpu_fused_schedule_discovery.cpp` and analyzed by
`tools/analyze_cpu_fused_schedule_discovery.py`. Full artifacts:
`trace/cpu_fused_schedule_discovery/`.

## 1. Initial Audit Findings

- `src/kernels/cpu_kernels.cpp` and `apps/run_mlir_fused_kernel_benchmark.cpp`
  already implement a 4-variant fusion-attribution ladder (naive/tiled ×
  unfused/fused), but **only one fixed tile size (32×32×32)** for the fused
  path — there was no apples-to-apples schedule (tile-shape) candidate tier
  before this phase. The existing `--mode use-plan` dispatcher already
  enforced `tile_m == tile_n == tile_k` (rejecting asymmetric tiles), so
  schedule candidates with independent block dimensions required a new,
  separate tool rather than extending that dispatcher.
- The one real fused kernel (`matmul_postop_relu_tiled_one_pass_f32` /
  `fused_matmul_add_relu_optimized`) is: **serial** (no threading), loop
  order `ii(M)→jj(N)→kk(K)→i→k→j` with a tile-local `float` accumulator
  (no full-size intermediate tensor), single store pass, **no explicit
  SIMD intrinsics** — vectorization comes only from `-O3` auto-vectorizing
  the innermost `j` loop over contiguous memory. This structure was reused
  unchanged as the shared skeleton for Phase 1's candidates.
- Build flags: root `CMakeLists.txt` sets no explicit optimization flags;
  the local `build/` directory was configured `-DCMAKE_BUILD_TYPE=Release`
  → `-O3 -DNDEBUG`. No `-march=native`; on this arm64 host NEON is the
  architecture baseline (confirmed via `hw.optional.neon=1`), so no
  compiler-flag asymmetry exists between candidates.
- Timing (`include/utils/timer.h`) wraps only the iteration loop; tensor
  allocation, input fill, and reference computation happen outside the
  timed region — confirmed by direct inspection, and replicated in the new
  tool.
- Existing correctness comparison (`compare_outputs`) uses one shared
  `atol=1e-4, rtol=1e-4` tolerance against a naive reference — reused
  identically here.
- `tools/run_matmul_postop_multi_shape_evaluation.py` /
  `benchmarks/matmul_postop_workloads.json` are an orchestration layer over
  the existing 4-variant fusion-attribution comparison; they were **not
  modified** and remain a separate baseline (fusion attribution, not
  schedule selection).

## 2. Candidate Contract

One shared parameterized kernel skeleton
(`run_fused_tiled_matmul_bias_relu(input, weight, bias, output, M, N, K, block_m, block_n, block_k, thread_count, tile_scratch)`),
identical loop order/vectorization/fusion policy across all four candidates:

| candidate_id | block_m | block_n | block_k | thread_count |
|---|---|---|---|---|
| bm8_bn8_bk32 | 8 | 8 | 32 | 1 |
| bm16_bn16_bk32 | 16 | 16 | 32 | 1 |
| bm32_bn32_bk32 | 32 | 32 | 32 | 1 |
| bm8_bn32_bk32 | 8 | 32 | 32 | 1 |

Controlled variables (identical across all four): semantics
(MatMul+Bias+ReLU), dtype `f32`, accumulator dtype `f32`, fusion status
(one-pass fused, 0 full-size intermediates), launch count (1), row-major
input/output layout, thread policy (serial, `thread_count=1`),
vectorization policy (compiler auto-vectorization only), correctness
tolerance (`atol=1e-4, rtol=1e-4`).

**Serial-execution caveat (per phase spec):** thread_count is fixed at 1
for every candidate this phase. *This validates serial CPU tiling
behavior, not multicore hardware-capacity scheduling.* Physical/logical
core facts were recorded (10 total: 4 performance + 6 efficiency cores) but
not exercised.

The naive fused reference used for correctness (`run_naive_fused_matmul_bias_relu`)
is untiled and independent of all four candidates — it is not part of the
candidate set it validates.

Methodology: input distribution `uniform(-1,1)` via seeded `std::mt19937`
(seed=1234, shared across all candidates and the reference per workload);
correctness tolerance `atol=1e-4, rtol=1e-4`; candidate execution order
**rotated every repeat** (round-robin) to reduce thermal/order bias;
measurement budget scaled by FLOPs (tiny: warmup 50/iter 200/repeats 7 —
large: warmup 5/iter 10/repeats 5) to bound total runtime (~8 minutes for
all 30 workloads × 4 candidates); Timer wraps only the iteration loop.

## 5. Correctness Results

All 4 candidates passed correctness (`atol=1e-4, rtol=1e-4`) against the
independent naive reference on **all 30 workloads** — 120/120 candidate ×
workload correctness checks passed. Zero `correctness_failure`
classifications. The fusion-attribution baseline (below) also passed
correctness for both its unfused and fused paths.

## 6. Oracle Results

Real measured winner counts across 30 workloads (`winner_regions.json`):

| Candidate | Raw ranking wins (any_winner) | Noise-clearing stable wins |
|---|---:|---:|
| bm8_bn8_bk32 | 0 | 0 |
| bm16_bn16_bk32 | 1 | 0 |
| bm32_bn32_bk32 | 26 | 1 |
| bm8_bn32_bk32 | 3 | 0 |

Classification breakdown (30 workloads): `stable_winner`=1,
`near_tie`=1, `noisy_inconclusive`=28, `candidate_failure`=0,
`correctness_failure`=0.

The single stable win (`skinny_wide_m32_n4096_k2048`, margin 2.49% vs. a
2.00% noise floor) is a bare-margin result, not a robust region.

**Reproducibility check:** an earlier full run (before the fusion-attribution
baseline was added) showed `bm8_bn32_bk32` apparently winning the
`large_regular` family by 5–6% margins. The final run reported here shows
`bm32_bn32_bk32` winning the same shapes by <1% margins. This is exactly
the run-to-run noise the phase spec warns about — the noise-aware
classifier correctly caught both as *not* stable (`noisy_inconclusive`)
rather than reporting a flip-flopping "decision boundary" as real.

## 7. Candidate Decision Boundaries

No genuine, reproducible multi-region decision boundary exists in this
candidate space. `bm32_bn32_bk32` is at or near the best latency
essentially everywhere; the only other candidate that comes close
(`bm8_bn32_bk32`, which shares `block_n=32` — notably equal to one 128-byte
NEON cache line of `f32` values, `32 × 4 = 128`) never separates from it by
more than noise. `bm16_bn16_bk32` and especially `bm8_bn8_bk32` are
consistently and substantially worse (see static-policy regret below),
which **is** a large, real, non-noise effect — but it produces one clear
loser tier, not a second winner region.

## 8. Static Policy Comparison

Regret of always using one fixed candidate vs. the per-workload oracle,
across all 30 workloads (`static_policy_comparison.json`):

| Policy | Mean regret | Median regret | P95 regret | Max regret |
|---|---:|---:|---:|---:|
| bm8_bn8_bk32 | 187.6% | 195.9% | 201.2% | 266.1% |
| bm16_bn16_bk32 | 46.0% | 49.7% | 54.4% | 68.8% |
| bm32_bn32_bk32 | 0.08% | 0.00% | 0.47% | 1.03% |
| bm8_bn32_bk32 | 0.95% | 0.55% | 2.58% | 6.18% |

`bm32_bn32_bk32` as a fixed, never-adapting policy is within ~1% of the
oracle everywhere measured — which is itself the clearest evidence that no
adaptive selector is needed for *this* candidate space.

## 9. Plan/Dispatch Validation

All 4 candidates: `plan_matched_runtime = true`, **0 total overrides**
(`plan_dispatch_validation.json`). The dispatcher hard-rejects (does not
silently substitute) both an unknown `candidate_id` and a `block_m/n/k`
value that does not match its registered candidate — verified by
`tests/assert_cpu_fused_schedule_rejects_unknown_candidate.py`.

## 10. Fusion Attribution Baseline (kept separate from the schedule oracle)

Fixed shape M=256,N=256,K=512, tile config 32×32×32 (matches the dominant
schedule candidate, but this is a *different* experiment — comparing
launch/intermediate structure, not tile shape):

- Unfused (tiled matmul → separate bias-add → separate ReLU; 3 launches, 2
  full-size intermediates): mean **6.322 ms**, correctness passed.
- Fused (same tiled matmul, one-pass fused bias+ReLU; 1 launch, 0
  full-size intermediates): mean **3.257 ms**, correctness passed.
- **Fusion speedup: 1.94×  (48.5% latency reduction).**

This is a real, substantial, and separately-attributed finding: fusion
itself is clearly valuable on this CPU. It says nothing about which tile
schedule to pick — that is answered independently in §6–8.

## 11. Phase 1 Verdict

**`FAILED_FOUNDATION`**

One candidate (`bm32_bn32_bk32`) dominates the raw ranking (26/30) and is
the only candidate that ever clears the noise floor (1/30, at a bare
margin). No second, reproducible winner region exists — the one
apparent second contender's wins do not survive a repeat run. Per the
phase's own success criteria, this is reported honestly rather than
massaged into a false "SUCCESS."

### Minimum candidate-space change diagnosis (per spec §13)

The likely reason one candidate dominates: every candidate's tile working
set (`block_m × block_n × 4` bytes ≤ 4 KiB) is tiny relative to this CPU's
measured L1D (64–128 KiB) — no candidate is large enough to hit a genuine
capacity boundary, and `block_k` (the reduction tile) was **held fixed at
32 in all four candidates** — it was never varied at all. The two
`block_n=32` candidates (which happen to equal one 128-byte cache line of
`f32` values) are the strongest performers; `block_m` alone contributes
almost nothing once `block_n=32` is fixed. This points to two concrete,
minimum changes for a follow-up candidate-space revision (not implemented
in this phase): (a) vary `block_k` independently (it was never exercised),
and (b) test larger tile sizes (64/128/256) so working sets start to
approach real L1D/L2 capacity and can produce a genuine capacity-driven
trade-off, rather than only exercising loop-overhead/vectorization-width
differences at a scale where cache capacity is never actually a factor.

## 12. Hardware Abstraction Readiness (Phase 3 preview)

CPU facts were collected honestly and are sufficient groundwork for a
future Phase 3 hardware-capacity abstraction (core counts, per-cluster
cache sizes, cache line size, SIMD baseline — all sourced from `sysctl`,
none fabricated). However, this phase's schedule-candidate evidence does
**not** yet justify a hardware-capacity-driven schedule model, because no
candidate in this space was ever large enough to exercise the recorded
cache capacities. Phase 3 hardware-abstraction work can proceed on the
*capability* side independent of this result, but any schedule-decision
cost model built on top of it should wait for a revised candidate space
(§11) that actually produces capacity-driven trade-offs.

## 13. Remaining Risks

- **Threading not exercised**: all candidates ran serial
  (`thread_count=1`); this CPU's heterogeneous P/E-core split was recorded
  but never used. A multicore experiment is a separate, later phase by
  design (spec §3) and could reveal an entirely different decision
  surface.
- **Packing not implemented**: no explicit data-packing/repacking variant
  was tested; the observed dominance of `block_n=32` may partly reflect
  packing-free access patterns that a packed microkernel would change.
- **Vectorization is compiler-dependent**: all candidates rely solely on
  `-O3` auto-vectorization; results are specific to this compiler/flags and
  may differ under a different toolchain or with explicit intrinsics.
- **Benchmark representativeness**: 30 workloads is a documented,
  representative subset (not the full Cartesian product) chosen to bound
  runtime to ~8 minutes; a larger sweep could reveal a currently-hidden
  decision boundary, though the extremely consistent regret pattern across
  all six families makes a hidden boundary unlikely without a
  candidate-space change.
- **Single-host, single-session measurement**: results are from one
  machine, one build. The large_regular flip observed between two
  independent runs of this same tool (see §6) shows that even "wins" near
  the noise floor should not be trusted without repeat-run confirmation —
  which the classifier already accounts for by requiring a documented
  margin-over-noise threshold.

## 15. Recommended Next Coding Phase

Do not proceed to Phase 2 (build a schedule selector) on this candidate
space — there is nothing non-trivial to select among (one candidate is
within ~1% of oracle everywhere). Recommended repair before any selector
work: revise the Phase 1 candidate space to (a) vary `block_k`
independently and (b) include tile sizes large enough to approach measured
L1D/L2 capacity, then re-run this same discovery tool
(`run_cpu_fused_schedule_discovery`, extended with a wider candidate list)
to check for a genuine multi-region decision boundary before committing to
Phase 2's selector-validation work.
