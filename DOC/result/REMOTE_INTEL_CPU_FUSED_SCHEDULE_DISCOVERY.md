# Remote Intel CPU Fused Schedule Candidate Discovery — Phase R1 Result

Roadmap phase: **Phase R1 — Remote Intel CPU Schedule Candidate Discovery**
(remote-Linux compiler roadmap; `ml-graph-compiler-runtime`). Preceded by
Phase R0 (environment/target-profile truth audit, passed — see
`trace/remote_linux_baseline/` and the R0 report delivered separately).

Primary question: does the real remote Intel CPU have a meaningful,
apples-to-apples fused MatMul+Bias+ReLU schedule-selection problem with at
least two stable winner regions?

**Verdict: `FAILED FOUNDATION`** — after a spec-directed candidate-space
repair (BLOCK_M/N/K sweep spanning small/near-L1/above-L1/rectangular tile
footprints, varying `block_k` for the first time), one candidate
(`bm128_bn128_bk32`) still dominates the raw ranking and is the only
candidate that ever clears the noise floor — but now with much stronger,
**3-session cross-validated** evidence than either the original Apple M5 or
Intel-pilot result had. This is reported as a valid engineering result, not
worked around. Local Apple M5 measurements were **not** used anywhere in
this analysis (see §3).

All numbers below are real measurements from `allen-ZenBook-UX534FTC-UX534FT`
(Intel Core i5-10210U, Ubuntu 26.04), generated by
`apps/run_cpu_fused_schedule_discovery.cpp` and analyzed by
`tools/analyze_cpu_fused_schedule_discovery.py` /
`tools/aggregate_cpu_fused_schedule_sessions.py`. Full artifacts:
`trace/remote_intel_cpu_fused_schedule_discovery/` (remote host).

## 1. Portability Fixes Made Before Running Remotely

The Phase 1 (Apple M5) tool was reused, with three real portability bugs
found and fixed (not merely "checked" — each would have produced a wrong or
misleading artifact on Linux):

1. **Compiler identity**: the tool unconditionally shelled out to
   `clang++ --version`. On this remote host, `clang++` happens to be
   installed *and* CMake is configured to build with `/usr/bin/c++` (g++
   15.2.0) — the tool would have silently reported "clang 21.1.8" as the
   build compiler when g++ actually built the binary. Fixed by making the
   compiler-family macro (`__GNUC__`/`__clang__` + `__VERSION__`) the
   authoritative source, with the shell-invoked binary kept only as a
   supplementary string.
2. **Linux hardware facts were stubbed**: `physical_cores`, and
   `simd_capability` were hardcoded to `"unknown"` on the `__linux__`
   branch. Fixed to real queries (`lscpu` core-count arithmetic;
   `/proc/cpuinfo` flags for avx/avx2/avx512 detection).
3. **A hardcoded, unconditional "Apple Silicon hosts..." note** was written
   into every `environment.json`, regardless of platform. Fixed to a
   platform-neutral note; hybrid-core fields now read
   `not_applicable_non_hybrid_cpu` (honestly absent, never guessed) on this
   non-hybrid Intel part instead of describing Apple-specific topology.

Also added (needed for R1, not present in Phase 1): a `Provenance` block
(`target_host`, `git_commit`, `target_profile_id`, `utc_timestamp`) emitted
in every artifact; a `--target-profile-id` CLI flag with cross-target
dispatch rejection in `use-plan` mode; a `--candidate-set original|repaired`
flag (see §4).

Artifacts write to `trace/remote_intel_cpu_fused_schedule_discovery/`,
strictly separate from the Mac's `trace/cpu_fused_schedule_discovery/`
(never overwritten — see §3).

## 2. Build Environment Correction

The pre-existing `build/` directory on the remote host had
`CMAKE_BUILD_TYPE` **empty** (not `Release`) and was additionally
root-owned from an earlier container-based setup (not writable by `allen`,
found while investigating). Rather than escalate with `sudo rm -rf` on a
directory of unknown provenance, an existing allen-owned, already
Release-configured directory (`build-benchmark-release`) was reconfigured
and used instead — reversible, no permission escalation, no deletion of
unfamiliar root-owned state.

## 4. Remote CPU Candidate Contract

**Pilot (original Phase-1 tier, run first per spec):** `bm8_bn8_bk32`,
`bm16_bn16_bk32`, `bm32_bn32_bk32`, `bm8_bn32_bk32` — identical controlled
variables to Phase 1 (f32/f32 accumulator, one-pass fused, serial,
`thread_count=1`, compiler-auto-vectorization-only, `atol=rtol=1e-4`).
**Result: collapsed** — `bm32_bn32_bk32` won 24/30 raw rankings, 14/30
stable (noise-clearing), every other candidate 0 stable wins; mean regret
ranged from 0.23% (`bm32_bn32_bk32`) to 84.2% (`bm8_bn8_bk32`). Per spec:
*do not train a selector on this; perform a controlled repair.*

**Repaired tier (spec-directed BLOCK_M/N/K sweep)** — `block_k` varied for
the first time; tile footprints (`block_m×block_n×4` bytes, f32
accumulator) span from far below to above the real measured per-core L1D
on this host (32 KiB, verified via `getconf`/`lscpu -C`):

| candidate_id | block_m | block_n | block_k | footprint | category |
|---|---|---|---|---|---|
| bm16_bn16_bk16 | 16 | 16 | 16 | 1,024 B | small footprint, small K |
| bm32_bn32_bk32 | 32 | 32 | 32 | 4,096 B | Phase-1 baseline, medium K |
| bm64_bn64_bk32 | 64 | 64 | 32 | 16,384 B | near/half L1D, medium K |
| bm64_bn64_bk128 | 64 | 64 | 128 | 16,384 B | near/half L1D, large K |
| bm128_bn128_bk32 | 128 | 128 | 32 | 65,536 B | above L1D, medium K |
| bm128_bn128_bk256 | 128 | 128 | 256 | 65,536 B | above L1D, large K |
| bm16_bn128_bk32 | 16 | 128 | 32 | 8,192 B | rectangular (skinny-M/wide-N) |
| bm128_bn16_bk32 | 128 | 16 | 32 | 8,192 B | rectangular (wide-M/skinny-N) |

All controlled variables unchanged from Phase 1; no packing, manual SIMD,
or multithreading added — `thread_count=1` for every candidate.

## 5. Remote Benchmark Methodology

- **3 independent sessions**, run sequentially (not concurrently, to avoid
  cross-session CPU contention), each a fresh process invocation:
  `trace/remote_intel_cpu_fused_schedule_discovery/sessions/session{1,2,3}/`.
- Fixed input seed (1234) shared across all candidates and the reference,
  identical across sessions.
- Candidate execution order rotated per repeat (round-robin) within each
  session.
- FLOP-scaled budgets (7 repeats typical per session; 21 pooled repeats
  per workload/candidate after aggregation).
- Correctness (`atol=rtol=1e-4`) checked for every candidate on every
  workload, every session: **240/240** candidate×workload×session checks
  passed (8 candidates × 30 workloads × 3 sessions... within each session
  8×30=240 checks, so 720 total across 3 sessions — all passed).
- CPU affinity: **not controlled** (OS default scheduling) — recorded
  honestly in every `environment.json`, not silently assumed.
- Thread count fixed at 1 for every candidate, every session — this
  validates **serial** CPU tiling behavior only, not multicore
  hardware-capacity scheduling.
- `git_commit`, `target_host`, `target_profile_id`
  (`remote-intel-i5-10210u`), and `utc_timestamp` are embedded in every
  artifact via the shared `Provenance` block.

Pooled across all 3 sessions (21 repeats/workload/candidate), from
`trace/remote_intel_cpu_fused_schedule_discovery/oracle_winners.json` /
`winner_regions.json`:

| Candidate | Raw ranking wins | Noise-clearing stable wins |
|---|---:|---:|
| bm16_bn16_bk16 | 1 | 0 |
| bm32_bn32_bk32 | 0 | 0 |
| bm64_bn64_bk32 | 0 | 0 |
| bm64_bn64_bk128 | 0 | 0 |
| **bm128_bn128_bk32** | 13 | **1** |
| bm128_bn128_bk256 | 15 | 0 |
| bm16_bn128_bk32 | 1 | 0 |
| bm128_bn16_bk32 | 0 | 0 |

Classification breakdown (30 workloads): `stable_winner`=1, `near_tie`=1,
`noisy_inconclusive`=28, `candidate_failure`=0, `correctness_failure`=0.

**Cross-session validation (the actual "repeatable across sessions"
check)** — `session_summary.json`, `cross_session_conflict_count: 0`
(whenever multiple sessions independently called a workload
`stable_winner`, they always agreed on the winner). Three workloads had
*any* session call them stable:

| Workload | Sessions calling it stable | Winner(s) | Status |
|---|---:|---|---|
| `skinny_wide_m32_n4096_k2048` | **3 of 3** | `bm128_bn128_bk32` | **agree** — triply-replicated |
| `small_square_m128_n128_k2048` | 1 of 3 | `bm128_bn128_bk256` | did not replicate |
| `edge_heavy_m70_n70_k512` | 1 of 3 | `bm128_bn128_bk256` | did not replicate |

Only `skinny_wide_m32_n4096_k2048` is genuinely reproducible evidence — an
**independent, real, run-to-run collapse warning was avoided here**: a
single-session pilot on the repaired set (before pooling) showed session 1
alone reporting 2 distinct stable candidates (`bm128_bn128_bk32` **and**
`bm128_bn128_bk256`), while sessions 2 and 3 each independently converged on
only `bm128_bn128_bk32`. Pooling confirms sessions 2/3 were right: the
apparent second winner in session 1 was single-session noise, exactly the
failure mode Phase 1's spec warned about (*"Do not call a 0.1% difference a
meaningful boundary when run-to-run noise is 1%"*) — caught here by running
3 sessions rather than trusting one.

The repair did surface **real, large, non-noise structure** even though it
didn't produce a second stable-winner region: `bm128_bn16_bk32`
(wide-M/skinny-N) and `bm16_bn16_bk16` (tiny footprint) are catastrophically
worse (see §7), and the two above-L1D candidates
(`bm128_bn128_bk32`/`bm128_bn128_bk256`, both `block_n=128`) jointly capture
28/30 raw wins — strongly suggesting `block_n` width (inner-loop
vectorization span) is the dominant factor on this CPU, with `block_m` and
`block_k` contributing far less. This is a plausible, evidence-grounded
hypothesis (not a fabricated mechanism) but was not further isolated within
this phase's scope.

## 9. R1 Verdict

**`FAILED FOUNDATION`**

One candidate (`bm128_bn128_bk32`) dominates the raw ranking (28/30 jointly
with its `block_k=256` sibling) and is the only candidate to ever clear the
noise floor — now backed by 3-session cross-validation rather than a
single run. Per the phase's own criteria this is reported honestly.

### Exactly one next missing schedule dimension (per spec §9)

**Thread decomposition.** All measurement in R1 (both the collapsed
original tier and the repaired tier) is strictly serial
(`thread_count=1`), on a real 4-physical/8-logical-core CPU that was never
exercised. `block_n` width (vectorization span) is the dominant factor
found so far; the next-highest-value untested dimension is whether
splitting work across this CPU's 4 physical cores changes which tile shape
wins (larger tiles may amortize thread-launch/synchronization overhead
differently than small ones). This is *not* implemented in this phase, per
instruction.

## 10. Four-Pillar Gate After R1

- **Hardware Abstraction**: real Intel CPU facts (Phase R0) and real
  NVIDIA GPU facts (Phase R0: 16 SMs via `torch.cuda`, cc 7.5, ~3.9 GB
  usable VRAM) are both now identified from live queries, separable into
  hardware capacity (cores/cache/SM count) vs. candidate demand (tile
  footprint vs. L1D) vs. backend-specific provenance (`sysctl` and
  `os_query`/`torch.cuda` sources tagged per fact). **Not yet unified**
  into one canonical cross-backend abstraction — that is Phase R3.
- **Decision-making Compiler**: CPU is **not yet ready** — the repaired
  candidate space still has no genuine multi-region decision to compile a
  selector around. GPU (Triton, per the extensive pre-existing
  `trace/matmul_postop_triton_*` evidence located during R0) remains the
  system's strongest measured selector foundation.
- **AWQ Quantization Co-design**: untouched this phase, verified only.
  Real AWQ evidence exists and is reproducible: a real AutoAWQ artifact
  (`artifacts/qwen_awq/model.safetensors`, 449 MB, real quant_config
  w_bit=4/group=128/GEMM) and a real, measured vLLM AWQ serving benchmark
  (`results/qwen_quant/compiler_awq_short.json`,
  `"evidence_type": "measured", "status": "ok"`) both exist on the remote
  host. One stale artifact was found and flagged, not fixed:
  `results/qwen_quant/status.txt` embeds a **local-Mac path**
  (`/Users/allen/Documents/.../heterogeneous-inference-runtime/.venv/...`)
  and says `vllm not importable` — contradicted by the real measured
  result sitting next to it and by this host's actual working vLLM 0.24.0
  install. This is Mac-generated metadata that leaked into the remote
  checkout; it should be regenerated or removed in a later phase, not
  trusted as current status.
- **Hardware–Compiler Co-design**: not claimed complete. R1 establishes
  the second real, independent hardware/backend evidence source (Intel
  CPU, alongside the existing GPU evidence) needed for later joint
  decision work — no more than that.

## 11. Remaining Risks

- **Threading unexercised** (see §9) — the highest-value next dimension.
- **CPU under memory pressure during this run**: `free -h` showed ~870 MB
  free / 1.8 GB swap in use on this 7.1 GB laptop at measurement time
  (Phase R0 baseline) — not a dedicated benchmark server. Could add noise
  not present on a quieter host.
- **Fusion-attribution baseline is now stale relative to the repaired
  winner**: it measures a fixed 32×32×32 tile (matching Phase 1's Apple
  finding and the *original* Intel pilot's winner) and shows only a 1.005×
  (0.5%) fusion speedup here — starkly smaller than Apple M5's measured
  1.94× (48.5%) at the same tile config. This is a real, measured,
  correctly-labeled number, but the code comment claiming it "matches the
  schedule oracle's most common winner" is no longer accurate after the
  repair (the winner is now `bm128_bn128_bk32`). Flagged for a follow-up
  fix, not corrected here (would require re-running the baseline, which
  this phase's instructions do not call for).
- **Vectorization is compiler/flag-specific** (`-O3`, g++ 15.2.0, AVX2 —
  no AVX-512 on this CPU); results are specific to this toolchain.
- **30-workload subset, not full Cartesian product** — bounds runtime
  (~28 min/session × 3 ≈ 84 min total) but could miss a hidden boundary.
- **`build/` root-ownership anomaly** (§2) suggests this host's setup
  history includes at least one container-based provisioning step not
  fully reconciled with the current allen-owned checkout — worth a
  dedicated cleanup pass before heavier remote work (out of scope here).

## 13. Recommended Next Coding Phase

Do not proceed to R2 (CPU schedule selector) on this candidate space —
still nothing non-trivial to select among with genuine reproducibility
(one candidate within ~1.8% mean regret of oracle everywhere, triply
confirmed). Recommended: either (a) extend this same tool with a
thread-decomposition dimension (§9) and re-run the identical 3-session
protocol before reconsidering R2, or (b) proceed directly to **Phase R3**
(backend-neutral CPU/GPU hardware abstraction), since the GPU side already
has a materially stronger measured-selector foundation and R1's CPU facts
are sufficient to seed the abstraction's CPU half even without a CPU
schedule selector to attach to it yet.
